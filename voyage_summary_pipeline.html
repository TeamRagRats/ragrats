Stage 1 · Email Summaries
Hent emails uden summary

Første trin i Stage 1. Vi spørger databasen: hvilke emails mangler stadig en summary? En email er "pending" hvis den ikke allerede har en status='ok'-række i email_attach_summaries. Resultatet er en ordnet liste af emails, sorteret efter afsendelsestidspunkt.

📋 SQL — get_pending_emails()
SELECT
    e.email_id,
    e.voyage_key,
    e.sent_at,
    e.direction,
    e.body_cleaned
FROM emails e
WHERE e.email_id NOT IN (
    SELECT email_id
    FROM email_attach_summaries
    WHERE status = 'ok'
)
ORDER BY e.sent_at ASC NULLS LAST
[LIMIT {limit}]  -- kun hvis --limit flag er sat
↓ Output: Liste af { email_id, voyage_key, sent_at, direction, body } — én pr. pending email

Stage 1 · Email Summaries
Hent attachments for hver email

For hver email fra trin 1 hentes tilhørende vedhæftede filer. Kun filer der allerede er struktureret af Docling (i llm_structured-tabellen) inkluderes — rå binærer hoppes over. Indholdet er Markdown-struktureret tekst (tabeller, afsnit osv.).

📋 SQL — get_attachments(email_id)
SELECT
    a.file_path,
    ls.structured_md
FROM attachments a
JOIN llm_structured ls ON ls.sha256 = a.sha256
WHERE a.email_id = %s
  AND ls.structured_md IS NOT NULL
  AND TRIM(ls.structured_md) <> ''
↓ Output: Liste af { filename, content } — 0 eller flere attachments pr. email

Stage 1 · Email Summaries
Byg email summary prompt

Nu samles email-body og attachments til et LLM-prompt. Prompten er i to dele: en fast system-prompt der definerer rollen, og en user-prompt med det konkrete indhold. Se præcis hvad der sendes nedenfor.

🤖 SYSTEM PROMPT — system_prompts/summaries/email_summary.md
You are a shipping industry analyst. Your task is to write a concise summary
of a single email and its attachments from a bulk shipping operation.

Focus only on facts relevant to the voyage: cargo type and quantity, port names,
dates (laycan, ETA, ETD), freight rates, counterparty names, operational issues,
and any decisions or instructions. Ignore pleasantries and boilerplate.

Create 2-8 sentences in plain English. Do not use bullet points.
✉️ USER PROMPT — build_email_summary_prompt()
Direction: {INCOMING | OUTGOING}
Date: {2024-03-15 14:32 UTC}

Email body:
{body_cleaned — den rensede tekst fra emails.body_cleaned}

--- Attachment: {filename} ---
{structured_md — Docling-udtrukket Markdown fra llm_structured}

[gentages for hvert attachment med structured_md]

Create a 2–8 sentence summary of this email.
↓ Videre til: LLM API-kald (trin 4)

Stage 1 · Email Summaries
LLM-kald: email summary

Prompten fra trin 3 sendes til den lokale vLLM-server. 5 emails behandles parallelt (ThreadPoolExecutor med 5 workers). Ved fejl: op til 3 forsøg med exponential backoff (2s, 4s).

⚡ API REQUEST — LLMClient.chat_with_usage()
POST http://localhost:8002/v1/chat/completions

{
  "model": "{auto-detected fra /v1/models}",
  "temperature": 0.3,
  "max_tokens": 1024,
  "timeout": 300,
  "extra_body": {
    "chat_template_kwargs": { "enable_thinking": false }
  },
  "messages": [
    {
      "role": "system",
      "content": "{EMAIL_SUMMARY_SYSTEM — fra trin 3}"
    },
    {
      "role": "user",
      "content": "{build_email_summary_prompt(...) — fra trin 3}"
    }
  ]
}
↩ RESPONSE
response.choices[0].message.content  →  2-8 sætningers summary
response.usage.prompt_tokens          →  logges (ikke gemt i DB)
response.usage.completion_tokens      →  logges (ikke gemt i DB)
↓ Output: Tekst-summary pr. email (2–8 sætninger på engelsk)

Stage 1 · Email Summaries
Gem email summary i databasen

Summaries gemmes i email_attach_summaries. Batches af 20 emails committes samlet. Ved fejl gemmes fejlbeskeden i log-kolonnen med status='error'. Eksisterende fejlrækker slettes først (så de kan genprocesseres).

📋 SQL — ryd op + indsæt (batch commit pr. 20 emails)
-- Slet eksisterende fejlrækker for batch (så de kan genprocesseres)
DELETE FROM email_attach_summaries
WHERE status = 'error'
  AND email_id = ANY(%s);

-- Ved success (status='ok'):
INSERT INTO email_attach_summaries
    (email_id, voyage_key, sent_at, summary, status, log, generated_at)
VALUES (%s, %s, %s, %s, 'ok', %s, %s)
ON CONFLICT (email_id) DO UPDATE SET
    summary = EXCLUDED.summary,
    status = 'ok',
    log = EXCLUDED.log,
    generated_at = EXCLUDED.generated_at;

-- Ved fejl (status='error'):
INSERT INTO email_attach_summaries
    (email_id, voyage_key, sent_at, summary, status, log, generated_at)
VALUES (%s, %s, %s, '', 'error', %s, %s)
ON CONFLICT (email_id) DO UPDATE SET
    status = 'error',
    log = EXCLUDED.log,
    generated_at = EXCLUDED.generated_at;
✓ Stage 1 færdig. Alle emails har nu en summary-række i email_attach_summaries

Stage 2 · Voyage Summaries
Hent voyages uden summary

Stage 2 starter med at finde hvilke voyages der er klar: dvs. voyages der har mindst én ok-email summary, men endnu ikke en færdig voyage_summaries-række.

📋 SQL — get_pending_voyages()
SELECT DISTINCT voyage_key
FROM email_attach_summaries
WHERE voyage_key IS NOT NULL
  AND status = 'ok'
  AND voyage_key NOT IN (
      SELECT voyage_key FROM voyage_summaries
  )
ORDER BY voyage_key
[LIMIT {limit}]
↓ Output: Liste af voyage_key strenge, fx ["V2024-001", "V2024-002", ...]

Stage 2 · Voyage Summaries
Hent email summaries + fixture data

For hver voyage hentes to ting: (1) alle email summaries fra Stage 1, sorteret kronologisk — disse er "råmaterialet" til faseinddelingen; (2) fixture-data fra fixtures-tabellen, hvis den eksisterer for denne voyage.

📋 SQL — get_email_summaries(voyage_key)
SELECT
    s.sent_at,
    s.summary,
    e.direction
FROM email_attach_summaries s
LEFT JOIN emails e ON e.email_id = s.email_id
WHERE s.voyage_key = %s
  AND s.status = 'ok'
ORDER BY s.sent_at ASC NULLS LAST
📋 SQL — get_fixture(voyage_key)
SELECT * FROM fixtures
WHERE voyage_key = %s
-- Returnerer én række eller NULL (fixture er valgfri)
📋 SQL — get_existing_phases(voyage_key)
SELECT
    phase_index, phase_range, date_start, date_end,
    email_count, summary, status
FROM phase_summaries
WHERE voyage_key = %s
-- Bruges til at springe allerede-genererede faser over (idempotent)
↓ Output: N emails → splittes i batches af 50 → len(emails) / 50 faser (oprundet)

Stage 2 · MAP-fase
Byg phase summary prompt

Emailsummaries deles i faser af 50 ad gangen (PHASE_BATCH_SIZE = 50). For hver fase bygges en prompt der beder LLM om at opsummere netop det udsnit af voyage-historikken. Faser der allerede er genereret med status='ok' springes over.

🤖 SYSTEM PROMPT — system_prompts/summaries/phase_summary.md
You are a shipping industry analyst. You will receive a chronologically ordered
batch of email and attachment summaries covering part of a single voyage.
Each entry is tagged (INCOMING) or (OUTGOING), indicating whether the email was
received by the operator or sent by them. Use this direction to describe who
did what: INCOMING = a counterparty contacted us; OUTGOING = we communicated
to a counterparty.

Write a phase summary in plain English covering what happened in this slice of the voyage:
operational decisions, counterparty communications, cargo particulars, port calls, dates,
freight and commercial terms, operational issues, and any notable context. Do not restate
the same fact more than once. If multiple emails cover the same topic, consolidate into a
single statement. Reference specific dates when describing events.
Do not use bullet points. Do not speculate about events outside the given slice; this is
one phase of a larger voyage and later phases will cover subsequent events.

If any mistakes, errors, disputes, claims, incidents, or unforeseen events occurred in
this slice (e.g. stevedore damage, off-hire, delays, cargo claims, berthing issues,
weather problems, charterparty breaches), mention them inline with the relevant date.
The final voyage narrative will aggregate these across all phases.
✉️ USER PROMPT — build_phase_summary_prompt()
Voyage: {voyage_key}
Phase: {emails 1-50}

Email thread slice ({50} emails, chronological):
[1] {2024-01-10} ({INCOMING})  {email summary fra trin 4-5}
[2] {2024-01-11} ({OUTGOING})  {email summary fra trin 4-5}
[3] {2024-01-11 14:22 UTC} ({INCOMING})  {email summary fra trin 4-5}
... (op til 50 linjer)

Write the phase summary.
↓ Videre til: LLM API-kald pr. fase (trin 9) — faser køres parallelt med 1 worker (default)

Stage 2 · MAP-fase
Gem phase summary

Fase-summaries gemmes løbende efterhånden som de færdiggøres (ikke batched). Designet er delete-then-insert (idempotent): køres pipelinen om, overskrives kun de faser der mangler eller fejlede.

📋 SQL — _upsert_phase()
-- Slet eksisterende (idempotent ved genkørsel)
DELETE FROM phase_summaries
WHERE voyage_key = %s AND phase_index = %s;

-- Indsæt ny (ved success):
INSERT INTO phase_summaries
    (voyage_key, phase_index, phase_range, date_start, date_end,
     email_count, summary, status, log, generated_at)
VALUES (
    %s,                    -- voyage_key, fx 'V2024-001'
    %s,                    -- phase_index (0-baseret)
    %s,                    -- phase_range, fx 'emails 1-50'
    %s, %s,              -- date_start, date_end
    %s,                    -- email_count
    %s,                    -- summary tekst
    'ok',
    %s,                    -- log: fx 'OK 12.3s'
    %s                     -- generated_at (now UTC)
);
↓ Når alle faser er OK: REDUCE-fasen starter (trin 11–14) — alle phase summaries hentes fra DB

Stage 2 · REDUCE-fase
Byg fixture summary (hvis fixture findes)

Hvis der er fixture-data for voyagen (charterparty-aftalen), opsummeres den til et kort afsnit. Dette fixture-paragraph bruges som kontekst i det endelige voyage-summary. Har voyagen ingen fixture, springes dette trin over og der bruges en placeholder.

🤖 SYSTEM PROMPT — system_prompts/summaries/fixture_summary.md
You are a shipping industry analyst. Your task is to summarise a fixture record
from a bulk shipping voyage into a short paragraph.

Include: vessel name, trade route (load port -> discharge port), cargo type and
quantity, freight rate, laytime terms, and any notable clauses. Write 3-5
sentences in plain English.
✉️ USER PROMPT — build_fixture_summary_prompt()
Fixture data:
{fixture JSON — alle kolonner fra fixtures-tabellen, pretty-printed:
{
  "voyage_key": "V2024-001",
  "vessel_name": "MV EXAMPLE",
  "load_port": "Rotterdam",
  "discharge_port": "Singapore",
  "cargo_type": "Grain",
  "quantity_mt": 50000,
  "freight_rate": "USD 28.50/MT",

Write a 3–5 sentence summary of this fixture.

Stage 2 · REDUCE-fase
Byg voyage summary prompt

Det centrale REDUCE-trin: alle fase-summaries fra trin 10 og fixture-paragraph fra trin 11 samles i én stor prompt. LLM-opgaven er at integrere faserne til en sammenhængende voyage-fortælling — ikke blot genfortælle dem fase for fase.

🤖 SYSTEM PROMPT — system_prompts/summaries/voyage_summary.md
You are a shipping industry analyst writing an internal voyage report.

You will receive a fixture summary followed by a sequence of phase summaries
that together cover a complete voyage. Each phase summary was generated from
a slice of the email thread and already aggregates many emails. Your job is
NOT to retell each phase — your job is to INTEGRATE the phases into a single
coherent narrative of the whole voyage. Treat the phase summaries as source
material, not as sections you have to reproduce.

Emails in the underlying thread were tagged (INCOMING) — a counterparty
contacted the operator — or (OUTGOING) — the operator communicated to a
counterparty. Use this direction to describe who did what when it matters.

Hard rules:
- Do NOT structure the output phase by phase. Do NOT write headings like
  "Phase 1", "Phase 2", etc. Do NOT walk through the phases sequentially
  just because they appear in the input.
- Organise the narrative by the voyage lifecycle:
  pre-fixture and negotiation -> loading phase -> voyage -> discharge ->
  post-voyage issues. Dates drive the order, not the phase boundaries.
- Consolidate repeated or overlapping information: if several phases
  describe the same event (ETA updates, counterparty exchanges, weather
  delays), report the event once, with the relevant dates, and move on.
- Preserve specific facts: counterparty names, vessel movements, ports,
  cargo particulars, laycan/ETA/ETB/ETS, freight terms, demurrage/despatch,
  and any operational decisions. Drop pleasantries and duplicate ETAs.
- Plain English prose. No bullet points in the main narrative. Reference
  specific dates when describing events.

Length: aim for a detailed but focused narrative — roughly 2500-4000 tokens.
Prefer a tight, integrated story over an exhaustive enumeration. If you
find yourself reproducing a phase summary, stop and synthesise instead.

If any mistakes, errors, disputes, claims, incidents, or unforeseen events
occurred during the voyage (e.g. stevedore damage, off-hire, delays, cargo
claims, berthing issues, weather problems, charterparty breaches), add a
separate section at the end titled "Issues and Unforeseen Events" that lists
and briefly explains each incident with the relevant date. If no such
events occurred, omit this section entirely.
✉️ USER PROMPT — build_voyage_summary_from_phases_prompt()
Voyage: {voyage_key}

Fixture:
{fixture_paragraph fra trin 11
 — eller "(no fixture data available)" hvis ingen fixture}

Phase summaries ({N} phases, chronological):
=== Phase 1/{N}: emails 1-50 [{date_start} - {date_end}] (50 emails) ===
{phase summary tekst fra trin 9}

=== Phase 2/{N}: emails 51-100 [{date_start} - {date_end}] (50 emails) ===
{phase summary tekst fra trin 9}

=== Phase 3/{N}: emails 101-127 [{date_start} - {date_end}] (27 emails) ===
{phase summary tekst fra trin 9}

... (én sektion pr. fase)

Write a comprehensive voyage narrative that integrates all phases into a single coherent story.
↓ Videre til: Det største LLM-kald i hele pipelinen (trin 13) — max 16.384 output tokens

LLM-kald: voyage narrative

Det endelige og mest krævende LLM-kald. max_tokens er sat til 16.384 fordi voyage-narrativen skal være en detaljeret rapport på 2500–4000 tokens. Timeout er 300 sekunder for at give modellen tid til lange outputs.

    {
      "role": "system",
      "content": "{VOYAGE_SUMMARY_SYSTEM — fra trin 12}"

      "role": "user",

Én sammenhængende tekst organiseret efter voyage-lifecycle:

  [Pre-fixture og forhandling]

  [Discharge]
  [Post-voyage]

  Issues and Unforeseen Events   ← kun hvis der var hændelser

Mål: 2500-4000 tokens (~1800-3000 ord)
↓ Output: Færdig voyage narrative — én sammenhængende fortælling om hele voyagen

Stage 2 · REDUCE-fase
Gem voyage summary

Den færdige voyage narrative gemmes i voyage_summaries. ON CONFLICT sikrer at en genkørsel opdaterer eksisterende rækker i stedet for at fejle. Feltet has_fixture angiver om fixture-data var tilgængeligt.

📋 SQL — gem voyage summary
INSERT INTO voyage_summaries
    (voyage_key, summary, email_count, has_fixture, generated_at)
VALUES (
    %s,          -- voyage_key, fx 'V2024-001'
    %s,          -- summary tekst (2500-4000 tokens)
    %s,          -- email_count (total antal emails i voyagen)
    %s,          -- has_fixture (True/False)
    %s           -- generated_at (now UTC)
)
ON CONFLICT (voyage_key) DO UPDATE SET
    summary = EXCLUDED.summary,
    email_count = EXCLUDED.email_count,
    has_fixture = EXCLUDED.has_fixture,
    generated_at = EXCLUDED.generated_at;
✅ PIPELINE KOMPLET
Tabeller der er skrevet til i denne kørsel:
  email_attach_summaries   ← Stage 1: én række pr. email
  phase_summaries          ← Stage 2 MAP: én række pr. fase pr. voyage
  voyage_summaries         ← Stage 2 REDUCE: én række pr. voyage

Hele pipelinen er idempotent:
  → Genkørsel springer over allerede-OK rækker
  → Fejlede rækker overskrives ved næste kørsel
🏁 Færdig! Voyage summary er nu tilgængelig i voyage_summaries WHERE voyage_key = '{voyage_key}'
